# Repository Guidelines

## Project Structure & Module Organization
- `configuration.nix` is the root system entrypoint and defines imports plus global settings.
- `hardware-configuration.nix` is machine-specific hardware setup generated by NixOS.
- `modules/` contains feature modules (e.g., `networking.nix`, `media.nix`, `lsp.nix`).
- `modules/packages/` groups package lists by theme (e.g., `editors-devtools.nix`, `system-tools.nix`).
- `drivers/` holds GPU/driver-specific modules (`amd.nix`, `nvidia.nix`).
- `boot/` contains bootloader configuration (`grub.nix`).
- `local/` is optional and git-ignored for machine- or user-specific overrides.

## Build, Test, and Development Commands
- `nix eval -f ./configuration.nix` performs a fast evaluation check for obvious errors.
- `nix-instantiate -I nixos-config=./configuration.nix '<nixpkgs/nixos>' -A system` validates the full system configuration without building or switching.
- Always dry-run or evaluate first; do not apply changes directly from this repo.

## Tooling Restrictions
- Never use Nix flakes.
- Never use Nix Home Manager.
- Never run `nixos-rebuild` from this repository.
- Always dry-run and validate the configuration before any deeper changes.

## Coding Style & Naming Conventions
- Use 2-space indentation and idiomatic Nix formatting.
- Format Nix files with `alejandra` (installed via `modules/lsp.nix`).
- Keep module names descriptive and aligned to their concern (e.g., `modules/shared-fs.nix`).
- Group package lists by domain under `modules/packages/` rather than in `configuration.nix`.

## Testing Guidelines
- There is no automated test suite in this repo.
- Prefer `nix eval` and `nix-instantiate` checks to validate changes.
- Keep `local/` for untracked experiments and machine-specific overrides.

## Commit & Pull Request Guidelines
- Commit history uses Conventional Commits with optional scopes (e.g., `feat(nixos): ...`, `chore(vscode): ...`, `fix: ...`).
- Keep commits focused on a single module or concern.
- PRs should include a brief summary, rationale, and validation steps (e.g., `nix eval ...`, `nix-instantiate ...`).
- If a change impacts hardware or boot, call it out explicitly in the PR description.

## Security & Configuration Tips
- Put secrets or machine-specific tweaks in `local/` and keep them out of version control.
- Avoid editing `hardware-configuration.nix` unless hardware has changed or you regenerate it.
